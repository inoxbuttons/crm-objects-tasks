# Решения и допущения

Там, где ТЗ не даёт однозначного ответа, решения такие:

1. **Роль** хранится в `profiles.role` и задаётся при создании пользователя через `app_metadata` (меняет только админ с secret key). `user_metadata` пользователь может переписать сам, поэтому на роль она не влияет — это проверяется в security-check.
2. **Любой постановщик** видит и принимает/возвращает любые задачи, не только свои (ТЗ: «видит всё»).
3. **Исполнитель в карточке объекта** видит только свои задачи, а не все задачи объекта.
4. **Имена, email и роли** всех пользователей видны всем авторизованным — нужно для истории и выбора исполнителя. При желании можно ограничить.
5. **Удаление мягкое.** ТЗ одновременно требует, чтобы постановщик удалял задачи и чтобы историю нельзя было удалить через API. Поэтому физического DELETE через API нет: функция `delete_task` помечает задачу удалённой (`deleted_at`, `deleted_by`), RLS скрывает её из всех списков, а история статусов остаётся в базе. Удалить можно только задачу в статусе «Новая», по которой ещё не шла работа.
6. **Объект** удаляется так же мягко (`delete_object`) и только если в нём нет задач; в интерфейсе кнопка удаления у такого объекта скрыта. На удалённый объект нельзя поставить или перенести задачу.
7. **Принятая задача** закрыта: редактировать её нельзя.
8. **Переназначить исполнителя** и перенести задачу на другой объект постановщик может в любом статусе, кроме «Принята». В историю статусов это не пишется — история только про статусы, как в ТЗ.
9. **Исполнитель обязателен** при создании задачи, и им может быть только пользователь с ролью «Исполнитель» (проверяет триггер).
10. **Переходы, выполняемые исполнителем**, может сделать только назначенный исполнитель задачи — постановщик не может «взять в работу» за него.
11. **Справочник переходов** (`status_transitions`) хранится в БД и используется и функцией смены статуса, и интерфейсом (какие кнопки показать) — одно место правды.
12. **Исполнитель, обращаясь к чужой задаче через RPC**, получает «Задача не найдена», а не «нет прав» — чтобы не раскрывать сам факт её существования.
13. **Комментарий** обязателен при возврате на доработку (пустой или из одних пробелов не принимается). Функция смены статуса принимает необязательный комментарий и при других переходах, но в интерфейсе поле показывается только для доработки.
14. **Без realtime**: данные обновляются после действий и при переходе между экранами.
15. **Тестовые данные** создаются скриптом: пользователи — через admin API, а объекты, задачи и все смены статусов — от имени обычных пользователей через ту же RPC, что и в интерфейсе. Поэтому история в сиде настоящая.

## Технические заметки

- Хостинг — GitHub Pages (статический сайт). Rewrite там нет, поэтому `404.html` = копия `index.html`: прямые ссылки открываются, но сервер отвечает на них кодом 404 (для пользователя незаметно).

- Supabase по умолчанию выдаёт ролям API полные права на таблицы `public` — в миграции они отозваны (`revoke all`), включая права по умолчанию для будущих таблиц, и выданы точечно, в том числе поколоночно.
- Все `security definer` функции — с `set search_path = ''` и полными именами; служебные функции лежат в схеме `private`, которая не публикуется через API.
- Миграция 0007 — мягкое удаление (см. п. 5). Миграции 0004–0006 — исправления, найденные при прогоне (применённые миграции не редактировались): Supabase Auth записывает `app_metadata` отдельным UPDATE после вставки пользователя, поэтому роль синхронизируется и при обновлении.

## Не успели / вне скоупа

Сброс пароля, пагинация и поиск, вложения, уведомления, realtime-обновления, e2e-тесты интерфейса, журнал изменений полей задачи (кроме статуса), управление пользователями из интерфейса.
